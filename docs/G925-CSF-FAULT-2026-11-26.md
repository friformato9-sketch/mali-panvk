## Fault and nearest allocation

At 11:58:33.308, kbase reported:

```text
status 0x010002c2 (exception 0xc2)
sideband 0x000000711e004200
```

The CSF callback emitted the GPU mapping list immediately after the fault. It contains this VkDeviceMemory mapping:

```text
VkDeviceMemory 0xb40000737a71f350
VA 0x711a000000 .. 0x711e000000 (size 0x4000000)
```

The nearest preceding bound VkBuffer is:

```text
VkBuffer 0xb40000732a72d090
memory offset 0x3c00000
VA 0x711dc00000 .. 0x711e000000 (size 0x400000, usage 0x25)
```

The reported VA is **0x4200 bytes beyond both the VkBuffer end and VkDeviceMemory mapping end**. No mapping in the emitted map list covers `0x711e004200`. This identifies the nearest logical buffer allocation, but does not yet prove the faulting shader descriptor referenced that buffer. The descriptor set logging added for v6 is intended to establish that link.

## Interpretation and next step

The fault is an unmapped GPU VA immediately beyond the last buffer in the 64 MiB allocation, consistent with an out-of-range access. Treat it as a candidate buffer overrun until the v6 descriptor log ties the descriptor/binding to this VkBuffer. Do not extend the allocation or alter bounds handling based on address proximity alone.

For repeat runs, clear logcat before launch and redirect with PowerShell. Decode redirected logs as UTF-16 (`Get-Content` or Python `encoding='utf-16'`); raw byte searches miss the PanVK records because of PowerShell's UTF-16 output encoding.

The fault VA is 0x41c0 bytes beyond the exclusive end of both that 4 MiB buffer and the 64 MiB VkDeviceMemory mapping. No map-list entry covers the fault address.

The preceding work in the same command buffer consists of repeated GPU_CMD_DISPATCH operations, including workgroup grids 256x256, 128x128, 64x64, etc. The PANVK_PERF record for the relevant batch reports 3 command buffers and 12 calls, with 4 compute calls. The captured v9 log contains no GPU_DESC_BUFFER, GPU_DESC_BUFFER_VIEW, GPU_DESC_DYNAMIC_BUFFER, GPU_USE_DYNAMIC_BUFFER, vertex/index-use, or BDA records tying the adjacent buffer to a shader access.

This is now a stronger candidate than the v4-v8 vertex/index hypothesis, but it is still only an adjacency correlation. The latest diagnostic revision (v10, not yet runtime-tested) adds:
- compute shader and workgroup-local-size identity at each dispatch;
- used descriptor-set mask, heap usage, embedded-sampler metadata and the generated resource-table address/contents;
- conventional descriptor-set binds and dynamic offsets;
- descriptor-heap binds for resource and sampler heaps;
- image-view descriptor metadata and backing VkDeviceMemory plane addresses;
- descriptor-set copy operations.

The next run should use PANVK_DEBUG=startup,dump,perf (omit trace, which forces synchronous submission and changes the execution path). Correlate GPU_DISPATCH_STATE / GPU_RES_TABLE / GPU_RES_HEAPS / GPU_DESC_IMAGE with the faulting VA before changing allocation sizes or robustness handling.
